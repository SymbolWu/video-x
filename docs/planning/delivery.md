# video-x 实施 迁移与验收计划

实施基线 1.1 · 2026-11-17 · 对应 PRD 1.1、原型 V0.7、数据库候选 v0.5

2026-11-18 实施更新：同级 `video-x` 工程已创建，M0 字段登记完成，M1 三端真实资料切片已联调；用户随后安装 Docker，本机镜像构建、启动、内置 FFprobe 和容器重启验收现已通过。进度与证据见 [新工程阶段记录](../implementation/status.md)。

实施按可使用的产品闭环推进，每个阶段同时交付必要的领域规则、接口、界面和验证。新工程使用独立数据库与资源目录，现有 Web、后端和 Android 在切换前继续运行。

首版部署环境已经确定为当前 Mac，接受登录后自动恢复。下述时延与恢复目标为实施验收目标，需要在真实媒体盘和网络条件下测量。

## 0 现在可以开始什么

可以开始 M0 的开工收口和 M1 工程实施。现有材料足以建立工程边界、领域模型与首条真实 API 流程；不需要等所有页面继续精修。开发必须对照 [43 项旧能力](legacy-capability-baseline.md)、[PRD](product-requirements.md)、[查询规则](list-query-spec.md)和 [V0.7 录入交互](ingest-interaction-v07.md)，每项功能都有实施去向。

新工程已经实现资料 API、独立库迁移、账号、三端资料与个人状态切片；真实媒体播放、服务端录入草稿、旧库迁移及正式部署尚未完成。52 项原型检查和历史 79 项数据库检查不能代替这些实施验收。每个阶段是开发顺序，不是重新删减首版范围。

## 2 第一批工作的具体顺序

首批产物是可运行的新工程与真实资料切片，随后立即进入“一个真实文件”的可用闭环。没有通过验收的步骤不标记完成，暂不承诺日历工期。

| 顺序 | 具体任务 | 可检查的产物与退出条件 |
| --- | --- | --- |
| 01 固定产品与能力基线 | 使用 PRD 1.1、V0.7、L01～L43；登记建议、已确认决定、原型缺口 | 每项能力绑定阶段与验收，不把未画完当成取消；完整录入与全部筛选留在清单中 |
| 02 裁剪正式数据库范围 | 为候选表列登记首个启用阶段、依赖、来源、约束、迁移规则 | 明确首版启用、分阶段启用、用户已后置、待决定；生成有序迁移，禁止 ORM 启动自动改表 |
| 03 建立工程与边界 | 初始化独立仓库，Web/admin/server/android、契约与主题包，API/worker 两个入口 | 开发命令与配置示例能运行；Android 独立 Gradle 构建；浏览器不导入 ORM 或服务端内部代码 |
| 04 验证候选技术栈 | 事务与任务投递、重复任务/进程恢复、SQL 迁移、TS/Kotlin 客户端生成、镜像内 FFprobe | 留下可重复执行的样例与技术决定；失败先调整该选择，再扩业务；具体依赖版本写入 lockfile 和镜像清单 |

05～07 随资料切片一起交付，不等所有后端接口写完再做客户端。工程初期允许开发样例，但样例只验证资料 API；“真实录入/播放通过”必须等 08 的文件与设备证据。

### 2.1 每个功能的完成方式

每一项功能从同一条用户任务贯穿：业务规则与异常 → 数据约束与事务 → 请求响应契约 → API/worker → 管理和观看界面 → 集成验证与真实走查。涉及 Android 的契约变更同时编译和联调 Android。

每次交付记录对应 L/P/AC 编号、数据库变更、页面/API、实际执行的检查和剩余缺口。关键覆盖包括清空与不修改的区别、错误保留输入、筛选空结果、旧 revision 冲突、重试幂等、断网/离线。原型的 localStorage 逻辑不直接搬成正式业务规则。

### 2.2 M2 的首个可用闭环

选择服务器上的真实视频 → 探测并保存服务端草稿 → 完整填写或修正资料 → 人工确认 → 明确发布 → Web 和 Android 通过筛选找到作品 → 实际播放、退出、继续播放 → 修改正式资料并看到三端一致结果。

这条流程优先证明当前最重要的问题已经解决：资料能完整编辑、确认与发布分离、两端确实续播。来源接入和批次分组随后复用同一领域用例，不另建一套发布和关系逻辑。

### 3.1 代表性样例集

至少包含：单文件影片；1080p/4K 双版本；上下部/Part1/Part2 按集；同一集内多物理文件段；剧直接含集和可选季；一人两个名称与两个同名人物；同一人物多职责；跨分类人物及系列；重复文件副本；无封面/无在线匹配；已归档资料；离线根；损坏文件；新播放的精确断点、95% 未结束与旧进度明确排除；中文、日文与罗马字检索。

媒体样例选用有权使用的小文件，保留校验值。支持矩阵至少列出容器、视频/音频 codec、字幕、Web 浏览器与 Android 实机结果。对暂不支持的文件明确显示原因；首版可交付边界以实测矩阵为准，不以文件扩展名作保证。

### 3.2 初始质量目标

以当前约数千条顶层资料的量级建立测试数据。在同一 Mac、本机或正常家庭局域网、无转码与扫描争抢资源的基线下，资料列表与详情 API 的稳态 p95 目标不高于 500 ms，常用名称/详细名称搜索目标不高于 1 s。记录数据量、分页大小、缓存状态与并发条件；首屏图片懒加载，不把整库一次性传给客户端。

探测并发先从 2 配置起，测量 CPU、内存、盘读和播放卡顿再调整；来源并发和速率按站点单独限制。播放期间可以降低媒体探测优先级。性能目标不能用缓存固定演示数据的截图代替。

## 4 Mac 部署与恢复方案

### 4.1 产物与持久目录

同一提交产出 server 镜像（API 与 worker 两个命令）、gateway 镜像（观看/管理静态资源与 Nginx），以及 Android 构建产物。发布清单记录所有镜像 digest、契约版本、数据库 migration 版本与 Android 兼容范围。

| 内容 | 放置方式 | 更新与备份 |
| --- | --- | --- |
| PostgreSQL | Mac 内置盘上的独立持久卷 | 升级前备份；不随容器重建删除 |
| 图片、头像与附件 | 独立 assets 目录 | 与数据库按同一备份批次核对引用 |
| 原始媒体 | 登记的宿主媒体根目录，只读挂载 | 当前 API 与播放只读；整理 Worker 在独立验收后挂载指定的下载箱和目标目录 |
| 临时下载 | 有上限的 cache 目录 | 可清理；活跃资源不能被清理；remux 后置 |
| 运行配置与密钥 | 仓库外的权限受限目录 | 备份密钥以保证能恢复来源凭据；不进入镜像和日志 |

镜像提供 FFprobe/FFmpeg 固定版本及启动自检，不要求用户填写宿主二进制路径。API 与 worker 使用相同 schema 版本；FFprobe 通过参数数组执行，超时和取消可终止子进程。Linux 容器硬件加速作为后续能力，首版先验证普通探测和直接播放。

### 4.2 登录后的恢复链路

Docker Desktop 配置登录启动，容器使用适当的重启策略，正常恢复流程为：用户登录 → Docker 就绪 → 数据库及应用恢复 → 检查媒体根与代理 → 恢复可执行任务。登录启动与容器重启是两层机制。[Docker Desktop 设置](https://docs.docker.com/desktop/settings-and-maintenance/settings/)和[重启策略](https://docs.docker.com/engine/containers/start-containers-automatically/)分别说明了这两个条件。

媒体 bind mount 使用显式配置并禁止自动创建不存在的宿主目录，避免误把空目录当作媒体盘。启动工具先核验根标识；介质尚未挂载时保留诊断并有界等待。必要时交付一个用户级登录恢复任务，等待 Docker/卷可用后重试 Compose；正常启动不自动运行数据库迁移，也不覆盖用户主动停用服务的状态。[Compose 挂载配置](https://docs.docker.com/reference/compose-file/services/#volumes)支持阻止隐式创建源目录。

不把所有外盘绑定为整个 API 的就绪条件：资料、登录和任务查询尽量可用，文件投递或探测组件按根目录分别降级。若容器因缺失 bind 源根本未能启动，登录恢复工具应在卷恢复后重建所需组件。这个场景在 M1 实盘验证，再固定具体 Compose 服务拆分。

API `/health/live` 表示进程可响应，`/health/ready` 检查 DB 与 schema 兼容；媒体根、FFprobe、worker 和来源网络在受保护的诊断页逐项显示。HTTP 仍正常时的 unhealthy 状态不会自动等价于进程退出，需要有诊断或明确恢复动作。

建议验收目标：Docker、数据库和所需媒体卷均就绪后 120 秒内恢复页面与本地播放；来源连接恢复后 5 分钟内恢复可重试任务，429 等等待时间另算。Mac 睡眠和网络断开会暂停可用性，唤醒后验证会话、盘身份、租约和代理再继续。首版不以无人登录持续在线为目标。

### 4.3 抓取出站与本地访问

每个来源独立选择直连或代理，出站 HTTP 在 worker 中受控；镜像拉取代理与来源抓取代理分别诊断。容器内的 127.0.0.1 不当作宿主代理地址，地址从环境配置注入。需要宿主访问时按 Docker Desktop 的部署网络配置验证。[Docker Desktop 网络文档](https://docs.docker.com/desktop/features/networking/)说明了容器网络与宿主网络的区别。

只发布 gateway 所需端口，数据库、队列和代理控制面不开放到局域网。Android 真机联调时使用 Mac 的稳定局域网地址与受控会话；公网端口映射与远程访问不因抓取需求自动启用。来源允许域名、重定向与凭据作用域在服务端校验，日志脱敏。

## 5 CI 发布与恢复演练

| 检查层 | 内容 | 阻断条件 |
| --- | --- | --- |
| 每次变更 | 固定 lockfile、格式/lint、实际项目类型检查、领域与固定解析样例测试、契约生成差异、Web 构建、Android 编译 | 任一必需检查失败 |
| 涉及持久化 | 临时数据库迁移、外键唯一约束、合并/排序/分类并发、幂等发布 | 迁移失败或关系边界不成立 |
| 发布候选 | 镜像启动、FFprobe 自检、契约兼容、真实样例冒烟、迁移升级演练 | 镜像与受测提交不同或冒烟失败 |
| Mac 部署 | 预检→备份→独立 migrate→拉取固定 digest→切换→ready→业务冒烟 | 任一步失败停止推进；应用失败回旧镜像 |

CI 产物构建一次，服务器不重新拼装 workspace 或执行非锁定安装。基础镜像、Node、媒体工具和数据库的具体版本在 M1 验证后固定；后续升级经过同一流水线。

发布工具保存上一份发布清单并互斥执行，禁止两个部署同时迁移。先使用本地显式部署命令，CI 成功不直接发布到日常媒体库。数据库采用兼容迁移；回旧镜像前检查 schema 兼容，不能假设回滚镜像会还原数据库。破坏性迁移安排单独窗口和恢复计划。

数据库与资产建议每日备份，保留至少一个异盘副本；初始目标为资料与个人状态 RPO 不超过 24 小时、按演练步骤恢复服务 RTO 不超过 2 小时。RPO 是允许丢失的数据时间，RTO 是恢复服务所需时间；媒体本体的保护范围另列。每个发布候选及正式切换前至少做一次临时环境恢复，核对人物头像、收藏关系和断点。

## 6 旧库迁移与切换

### 6.1 迁移工具交付物

2026-11-16 已确认排除 task、actor_profile_task 的全部旧任务行及 result_url 指向的 JSON。新系统任务从切换后建立；不检查/导入旧任务结果，不恢复旧运行态。旧任务曾发布的影片与人物等正式资料仍迁移。

同日进一步确认排除 movie.watch_progress、movie.last_play_position_ms。新系统进度、事件、会话初始为空，不造迁移专用会话；resume_edition_id=NULL、takeover_generation=0、watched_at=NULL。喜欢、评分、收藏夹仍迁移，旧次数/最近时间仅作历史汇总。

工具分成只读盘点、导出、转换、目标导入、核对和报告六个命令。默认 dry-run，输出机器可读 JSON/CSV 与便于阅读的总结；真实导入只写新库。报告包含源导出标识、规则版本、根映射、映射数量、跳过/异常原因、校验值与时间。

| 核对对象 | 核对方式 | 切换阻断条件 |
| --- | --- | --- |
| 作品及旧父子结构 | 按真实类型映射计数，记录一个旧对象拆成多个新对象的原因 | 存在无法解释的丢失或错误分集/分段 |
| 人物与参演关系 | 人物映射、distinct 关系集、详细名称和来源编码 | 失联引用、错误合并、个人喜欢丢失 |
| 系列与分类 | 身份映射、成员集合、生成顺序标记、层级与可见性 | 父级环路、错误归属或旧编码映射不明 |
| 收藏夹与个人状态 | 成员集合、喜欢、评分、历史汇总；旧进度明确排除，新断点初始为空 | 不明原因缺失；来源评分被当个人评分；排除项被意外导入 |
| 文件与图片 | 原路径/根映射、stat、图片引用、抽样校验与离线清单 | 原视频被改写、在线文件无法定位、资源引用大量失效 |

原大小字符串保留在迁移导出，大小以重新 stat 为准。旧观看进度和毫秒断点仅留在旧库备份，不换算进新 progress，不作为异常项要求用户补录。历史喜欢时间允许 NULL，喜欢状态仍保留。真实无效资料留在异常清单中，必须能追溯，不能仅为了总数相等生成假数据。

### 6.2 切换步骤

1. 小样试迁并回看真实播放，修订映射规则；再全量 dry-run，处理阻断异常。
2. 新系统继续以独立数据和原片只读方式试用，避免两套平台共同移动文件或写同一数据库。
3. 正式切换窗口前做旧库、新库和资源备份，保存旧发布与配置；暂停旧端写入、抓取和自动任务。
4. 重做最终一致导出，按 legacy_map 对照重放到新库，补齐新增/修改、关系删除及个人状态；以完整快照差异为准，避免仅靠 updated_at 漏掉关系移除。
5. 核对报告与抽样通过后切换 Web 入口和 Android 服务配置，执行 AC-01、AC-04、AC-08、AC-10、AC-11 冒烟。
6. 建议观察 7 天后再决定旧库退役；期间旧系统只读，保留可启动的旧发布与备份。

切换后需要退回旧系统时，先冻结新端写入并导出新增变化；旧备份不包含新系统已产生的收藏、评分与断点。回退前明确这些变化的重放方式，不能一键切回后静默丢失。应用发布回退与整套数据回退是两个不同流程。
