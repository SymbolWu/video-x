# 重构方案复审 · 2026-11-17

本页保留 V0.5 复审记录；当前开工顺序以[实施计划 1.1](delivery.md)为准，手动草稿/发布前移至 M2，M4 扩展来源、批量与分集。

结论：保留“模块化单体 + API/worker 两个入口、作品与文件分离、来源提案人工发布”的主方向；当前交付仍是候选设计，不能把 58 张表和若干可点击页面直接视为首版实施范围。此次重点收敛规则、补齐列表查询，并修正互相冲突的文档。

## 2 工程结构复核

业务模块保持 catalog、library、ingest、metadata、personal、playback、identity、platform。模块拥有自己的写用例；跨模块业务只通过公开用例和事务协调，不允许适配器直接写 ORM。API/worker 共用 domain/application，不复制业务规则。UI 的同构列表能力应由共享查询契约驱动，观看与管理端分别呈现操作。

目前首版规模不足以证明需要微服务、独立搜索集群或通用动态插件市场。先将来源适配器作为受控内部包；仅固定 search/details/person/artwork 能力和提案格式，JavDB/Havtw 的差异通过适配器表达。第三方运行时插件的沙箱、权限和版本兼容后置。

Fastify/Drizzle/PostgreSQL/pg-boss 仍是待技术切片验证的选型，不是本轮已完成升级。M1要验证：同一事务写业务与outbox、任务重复投递、迁移回滚兼容、OpenAPI生成TS/Kotlin、镜像内FFprobe取消超时、Android与Web直连播放。不要在尚未证明事务/恢复方案前大规模搬接口。

## 3 实施前还缺的闭环

沿用[字段核对缺口](prototype-schema-review.md#3-仍缺哪些关键界面)：媒体根/挂载离线恢复、初始化和设备会话、完整文件改绑与分段、组/分集批量维护、多来源冲突复核、其余实体归档恢复、图片异常。

优先顺序调整为：

1. **M0结束前**：列表契约与默认口径、首版DDL裁剪清单、上下部样例、来源差异与发布决定的revision范围；关键空/错/离线页面。
2. **M1技术切片**：登录→一部作品/演员/收藏夹→完整查询与分页→两端查看→管理修改→刷新；固定契约并建立数据库约束与并发测试。
3. **M2真实媒体**：媒体盘身份、探测、Range和实际seek；MP4/MKV兼容按实际编码/设备列矩阵，不因选型文档而承诺支持。
4. **M3/M4关系与录入**：合并、完整成员重排、人工发布事务和任务恢复。未通过这些用例前不开始全量迁移。
5. **M5/M6运行与切换**：Mac登录后恢复、外盘晚挂载、代理断网恢复、备份还原、旧库只读试迁及最终增量。

Mac容器化方案保持登录后恢复目标，必须实测Docker/卷/代理依赖，不能把restart策略等同于服务完整恢复。部署产物、资料数据库与原片备份的范围分别记录；真实迁移排除全部旧任务和旧进度，其他资料按映射核对。以上为实施门槛，本轮没有修改旧应用、运行数据库或Mac设置。
