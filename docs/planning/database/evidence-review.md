## 3 先补齐已有业务，再收敛扩展

下表的“建议”尚未写入 v0.1 DDL；在完成修订前，不得将当前 DDL 用作真实迁移依据。

| v0.1 缺口或假设 | 现有依据 | 下一版设计处理 |
| --- | --- | --- |
| 待清理标记无专用去向 | `movie.marked_for_review`；MovieRatingService 批量更新；Web 筛选 | 保留明确的待清理状态。需先明确它作用于作品还是实际文件；与归档、来源差异复核分开 |
| 封面布局无映射 | `movie.cover_layout`；Web 允许编辑并按值展示横/竖封面 | 保留展示偏好与旧值映射；与图片宽高、用途分开 |
| 中文支持无同义字段 | `movie.supports_chinese`；抓取、筛选、Android 卡片均使用 | 分清“来源宣称”“人工确认”“本地轨道检测”。先无损保留旧判断及其不确定性，不能仅靠 media_streams 取代 |
| 演员详细名称未单独处理 | `actor.full_name / detailed_name / alias`；人物补全和搜索 | 先保留三者原文，样例核对后决定主展示名、来源名称和可检索别名如何分配；不盲目按标点拆分 |
| 标签丢失属性分组、分类归属、显示开关 | `tag.attr_value / category / is_visible`；Web 按 category 再按 attrValue 分组 | 新标签模型必须承接三项语义。复核前不把旧标签自动拆成 genres 与 tags，也不新增全局同名强制合并 |
| 旧业务编码的身份规则未写完整 | movie_code、actor_code、series_code、tag_code、coll_code、category_code 均存在 | 明确“内部旧主键、业务编码、来源页面 ID、影片发行编号”四类身份；serial_number 不能吞并 movie_code。为每类编码制定命名空间和可查询映射 |
| legacy_mappings 无 tag 目标外键 | 旧 tag 有 ID、code，且存在大量影片关联 | 补齐标签身份追溯的表达，不能只迁移影片关系而丢弃标签映射 |
| 旧进度无法直接满足新 playback_progress 的必填关联 | 备份只有百分比；当前代码另有毫秒列；新表要求版本、文件段、会话 | 迁移先区分真实断点、百分比和未知值；若需迁移专用会话，须显式标识来源，不计为真实播放事件 |
| 旧累计播放数与新会话次数相加规则未定 | movie.play_count；新 legacy_play_count 与 playback_sessions | 定义旧累计次数作为基数，新会话何时计数，重试和恢复不能重复增加；不补造历史会话 |
| extra_info 只按新格式描述 | 历史有 directors/makers；当前 JavService 写 director/studio | 两代格式都做有来源的规范化；无法识别的原文保留到受控迁移归档，不静默丢弃 |
| 旧 parent_movie_code 被直接推导为固定剧季集层级 | 现有代码只有父编码与分集序号，没有季号；父记录多数也有文件 | 对 14 组历史样例逐组判断语义，再确定通用父子结构、播放段与剧集层级的边界；暂不自动造季记录 |
| 非空、唯一、归档约束有新增假设 | 旧 title 等允许 NULL；旧收藏夹名称无唯一限制；is_deleted 无删除时间 | 检查运行库空值、同名、空白和已删除行；冲突须出具报告。归档时间不得冒充真实历史删除时间 |

## 4 哪些新增是有目的的，哪些应后置

新增字段可以来自已确定的行为，不要求旧库有同名列，但应能说明谁写、谁读、解决什么问题。

| 类别 | 代表字段/表 | 本轮判断 |
| --- | --- | --- |
| 现有数据拆分与规范化 | 作品、文件、演员、系列、分类、标签、收藏、个人状态 | 有依据；拆表后的迁移去向仍需补齐上述缺口。系列由一对多扩成多对多、成员顺序属于新选择，不算旧数据事实 |
| 导入流程与稳定任务的新结构 | 服务端导入草稿、候选、阶段、发布结果、任务检查点 | 与已规划的导入复核和重启恢复相符；属于设计新增，旧任务 result_url 指向的外部结果还需核对 |
| 多来源身份与人工维护 | provider、来源 ID、抓取时间、适配器版本、快照、字段锁定和差异 | 多来源既有 JavDB，也有 Havtw 简介抓取；插件化是用户明确方向。整套 14 表拆分、关系级来源和快照保留粒度仍是技术选择，需要成本评审 |
| 文件准确性与扫描保护 | 精确字节数、mtime、probe_result、探测状态、根目录身份 | 支撑媒体管理；旧 file_size 已格式化并有舍入，精确值要重读文件，不能从字符串承诺无损恢复 |
| 并发与重试控制 | revision、幂等 key、事件序号、播放接管代数、outbox | 能解决明确的覆盖/重复提交问题，但旧库没有对应数据；实现、保留周期和是否单独成表仍需按首版闭环决定 |
| 未确认的个人身份层级 | accounts、profiles、devices、auth_sessions 四层拆分 | 当前没有这些业务数据。用户为个人自用，外网主要用于出站抓取；不能据此推定公网观看、多资料档案或完整设备管理。须收敛认证方案与个人状态归属 |
| 提前扩展的资料字段 | people.birth_date、biography、sort_name；media_items.original_title、sort_title；credits.character_names；person_aliases.locale | 本次检查的现有实体与抓取写入中未找到直接依据。后置或移出首版；名称排序问题也应先明确实际搜索需求 |
| 提前扩展的资料类型 | writer/producer 职责，publisher/label 机构角色，网站评分/票数 metadata_ratings | 当前抓取有演员、导演、片商，没有这些字段的写入依据。具体适配器提供且产品使用时再加入 |
| 新来源与新文件类型 | NFO、本地 sidecar 来源、外挂字幕编排 | 用户要求可扩展来源，不等于已要求实现 NFO；当前没有对应数据证明。保留接口扩展点，功能与专用列后置评审 |
| 更丰富的版本描述 | edition.cut、language，导演剪辑版命名 | 文件分段有现有组织依据；多个剪辑版本、人工语言版本尚需核对实际文件和操作场景，首版先考虑默认播放版本 |
| 类型/标签双体系 | genres、media_genres、source_value_mappings | 来源词汇存在，但旧标签是另一套有分组的结构。先承接旧标签，再决定是否引入独立 genre 域及映射规则 |

“待验证”不表示永远不能设计这些能力，而表示它们不能被包装为已有业务必须保留的数据。表的拆分数量应由闭环复杂度决定，不预设首版必须落下 59 张表。

## 5 后续定稿门槛

1. 修订作品、标签、人物和个人状态模型，覆盖 103 个现有持久字段的去向；允许取消旧功能，但需要明确记录产品决定，不用“重构”隐含取消。
2. 为保留的新字段逐项登记：旧字段/新增需求依据、写入方、读取场景、空值语义、迁移转换或初始化方式。没有读取场景的未来字段先后置。
3. 以当前运行库的只读快照复核空值、同名、编码、父子、日期和数据质量；历史备份统计只作为本次证据。
4. 用真实样例验证普通影片、多文件父子、两种封面、中文标记、标签分组、人物详细名、两代 extra_info、收藏和断点。出具前后数量、关系、异常与字段保留报告。
5. 最后统一修改 DDL、ER 图、字段字典和迁移脚本，并验证业务事务。上一轮 36 项 SQL 检查只证明当时草案中的数据库约束正反例通过，不能证明需求覆盖或迁移无损。
