# 产品需求与数据库承接设计

候选结构 v0.5 · 2026-11-17 · 对应[产品需求文档](../product-requirements.md)与[旧能力清单](../legacy-capability-baseline.md)。

本次继续使用作品、版本、文件、来源和个人状态分离的结构。旧版完整编辑所需的大多数数据已有对应表；本轮增加的是草稿确认凭据和多版本文件绑定规则，没有为了补表单创建一套重复作品表。

当前候选结构为 **58 表、568 字段、127 外键**。在独立临时 PostgreSQL 实例执行成功，**79 项数据库检查通过**。其中 17 项新增检查验证确认失效、多版本段号及作品组发布；没有执行运行库迁移或真实入库。

## 1 业务对象的阅读顺序

```text
导入批次 import_batches
 └─ 草稿 import_items
     ├─ 完整待确认资料 draft
     ├─ 草稿版本 draft_revision ↔ 人工确认 reviewed_revision
     ├─ 来源候选 import_candidates → 原始快照 metadata_snapshots
     └─ 文件选择 import_item_files（草稿版本键 + 文件段号）
                 │ 人工确认 + 手动发布事务
                 ▼
作品 media_items ── 主分类 categories
 ├─ 演职员 credits ── 人物 people
 ├─ 系列成员 franchise_items ── 系列 franchises
 ├─ 标签 media_tags / 片商 media_organizations / 图片 media_images
 ├─ 播放版本 editions ── 文件段 edition_parts ── 文件 media_files
 │                                                └─ 轨道 media_streams
 ├─ 个人状态 user_media_state / 收藏夹 collection_items
 └─ 子集 media_items（parent_id），每集独立拥有版本与个人状态

来源快照 → metadata_change_sets（提案）→ 人工接受 → 正式字段/关系
                                          └─ field_state 记录来源与人工锁
```

图片资源通过 assets 保存，业务表只持有引用。数据库内部 ID、来源 ID 和用户看到的编号分别承担身份、来源定位和检索职责。

## 2 本轮修正的具体结构

| 表与字段 | 变更 | 来源与作用 | 使用位置 |
| --- | --- | --- | --- |
| import_items.draft_revision | 新增正整数，初始 1 | 旧系统没有；用户要求人工确认必须对应明确内容 | 保存草稿、来源重选、文件改绑、发布冲突 |
| import_items.reviewed_revision | 新增可空正整数 | 旧系统没有；记录确认的是哪个草稿版本 | “已确认”状态、发布前校验 |
| import_items.reviewed_at | 新增可空时间 | 旧系统没有；记录本次明确确认发生时间 | 确认摘要、操作追溯 |
| import_items.reviewed_by | 新增可空账号外键 | 复用单账号，不引入多账户产品 | 区分人工决定与后台自动任务 |
| import_item_files.edition_key | 新增草稿内版本键，默认 default | 旧单文件结构拆分后的新需求 | 一个草稿的多个版本分别管理文件段 |
| import_item_files 主键与唯一约束 | 改为 item + edition_key + file；每版本 part_no 唯一 | 旧候选结构只允许整个草稿一套段号 | 两个版本都可以有“第 1 段” |
| import_batches.mode | 增加 manual 枚举 | 手动资料录入，旧流程没有独立入口 | 不依赖爬取或文件的未发布草稿 |
| import_items.draft_schema_version | 新草稿默认 2 | 完整编辑的版本化草稿协议 | 服务端校验、后续升级草稿 |
| published_edition_id | 作品组/剧/季发布时允许为空 | 先前候选约束错误地要求所有条目都直接播放 | 上下部作品组发布 |

没有给标题、简介、演员、系列、标签、片商、图片、评分等重复增加列；它们继续使用现有候选表。字段字典和来源说明已同步新增字段。

## 3 人工确认与发布的约束

`revision` 表示整行并发版本，包括任务状态；`draft_revision` 只表示需要人核对的内容版本。后台任务刷新错误状态不应让用户无故重复确认。

1. 创建草稿时确认人、确认时间、确认版本均为空。
2. 修改 draft、草稿协议版本、选中候选或文件绑定，递增 draft_revision，清空全部确认字段；ready 回到 matched。
3. 确认命令提交 expectedDraftRevision，服务器比较后写 reviewed_revision、reviewed_at、reviewed_by。三项必须同时为空，或同时有效且确认版本等于当前草稿版本。
4. 发布必须同时满足人工确认凭据、当前资料有效、文件核验及本次明确选中集合；发布阶段仅凭 ready 不足以放行。
5. 任务重试恢复同一次发布幂等键，不生成新授权。已发布的导入草稿与其原始文件选择不可原地修改；后续资料维护使用正式作品命令。

新增数据库触发器覆盖草稿/候选变动、文件关系增删改及确认失效。演员、系列等共享资料的外部变化和根目录/文件内容修订仍需发布事务重查 expectedRevision、content_revision，不能把行级触发器当作全部业务校验。

发布普通影片/分集/视频时必须引用该作品的正式版本；发布作品组/剧/季不能引用播放版本。分集组的父项和选中子集在同一用例中校验、创建、关联；SQL 仅允许结构合法，不代替“本次选择是否完整”的应用校验。

## 4 完整草稿如何保存

草稿允许不完整，所以不提前插入正式 people、franchises 或 media_items。`draft` 使用版本化 JSON，保存编辑内容；`import_item_files` 保存经过服务器授权与存在性校验的文件引用。禁止仅把任意客户端 JSON 不经校验复制到正式表。

| 草稿分区 | 保存内容 | 发布去向 |
| --- | --- | --- |
| media | 标题、编号、简介、备注、发行精度、中文标记、封面布局、形态、父级/集号 | media_items、media_identifiers |
| credits | 已有人物 ID 或草稿临时人物、职责、顺序 | people、credits；复用与新建分别处理 |
| categories/tags/series/organizations | 主分类、关系选择、临时新建资料、关系顺序 | 各主体表及关系表 |
| images | 已接收资源 ID、用途、顺序；尚未成功的上传状态 | assets、media_images；失败资源不能替换现有封面 |
| editions | 草稿版本键、名称、默认标记、备注、文件段引用 | editions、edition_parts |
| source choices | 选中来源身份/快照、逐字段决定、人工锁定 | source_records、provider_*、field_state、relationship_sources |
| pending group | 同批次临时父项身份 | 发布事务生成正式父 ID，再绑定分集 |

协议要限制允许字段、字符串长度、枚举、UUID/临时键、集合大小和深度；明确空值与空集合的意义。文件大小、编码、时长、根路径、源快照和系统 ID 由服务器读取，不接受表单伪造。HTML 中的图片 Data URL、虚构文件路径与 camelCase 样本只是演示存储，不是上传 API 或正式草稿协议。

## 5 编辑与清空语义

更新命令使用字段白名单与 expectedRevision。字段未提交代表不修改；可空字段提交 null 代表清空；关系提交完整空集合代表移除该类关系。个人喜欢/评分/已看不在资料更新 DTO 中，避免沿用旧接口缺省值导致状态重置。

发布草稿的关系更新和正式资料更新共用校验规则。编辑共享人物明确提交人物 ID 与其版本，不能将嵌入影片表单的同名人物内容自动扩散到其他作品。人工输入和来源接受分别记录写入来源，备注只接受人工修改。

## 6 筛选排序的数据依据

| 恢复的能力 | 数据与查询规则 |
| --- | --- |
| 评分上限/区间/包含未评分 | user_media_state.rating；评分区间与 NULL 的组合显式表达；0 不代表未评分 |
| 播放次数 | legacy_play_count + 同 profile/media 下 has_started=true 的会话数；同一会话只有一行，重复 start 不增加 |
| 组的播放次数 | 展示该组旧历史基数 + 新系统后代实际会话计数；不累加子集旧基数，避免旧父子历史重复累加 |
| 入库天数/日期 | media_items.created_at；旧时间保留其实际来源，不能宣称旧文件 birthtime 一定是入库时刻 |
| 完整发行日期范围 | 仅 release_precision=day 的 release_date 参与；只知年不补造日期，年份筛选单独提供 |
| 576p/480p | 默认版本各段主视频高度取最低值；540～719、360～539 是对旧宽泛档位的规范化；更低单列 |
| 多版本时长/体积 | 默认版本各段求和；任一未知则聚合未知；组容器为不适用 |
| 收藏夹复制/移动 | collection_items 的存在性、目标追加位置、源成员删除在同一事务；重复目标关系不导致移出丢失 |

播放次数是有效起播会话次数，不是完播次数或观看时长。has_started 只在播放器实际定位并开始播放后设置；暂停、心跳、网络重试都复用同一会话。若后续需要清理会话，应先建立不重算的累计归档规则；首版不删除已计数会话而改变历史次数。

这些能力使用既有字段和查询投影，不新增筛选表、排序表或存储格式化大小。排序必须在分页前完成，NULL 固定最后，同值稳定 ID 收尾。

## 7 验证与剩余边界

新增 17 项数据库检查覆盖：新草稿未确认、部分确认无效、确认绑定版本、任务进度不误清确认、资料变动失效、旧确认拒绝、文件绑定变动失效、多版本首段、同版段号唯一、未确认发布拒绝、普通影片必须有版本、组无版本发布、已发布草稿不可重写、已发布导入文件不可再改绑；缺少确认版本的凭据被拒绝；发布阶段不可回退以绕过锁定；发布确认收据不可重写。

正式应用还需要验证：批次原子发布、候选身份重查、共享资料并发、文件内容变化、清空 DTO、图片资源状态、任务重复执行和真实续播。候选结构仍包括后置领域，首版 migration 继续按产品范围裁剪；本次测试并未完成生产迁移或部署。

## 8 列表核对与容器交互修订

产品 1.1 / 原型 V0.7 将核对主入口放回结果列表。完整度来自当前草稿字段的计算，获取状态来自任务与执行结果，人工确认仍对应 reviewed_revision；三者不能混成一个状态或完整度百分比。未确认条目允许勾选、分组，发布仍需明确确认和选择。

容器由用户选定某一集复制资料，清除原编号和来源身份，不复制版本/文件；各集仅增加临时父项和集号。发布映射为 media_items 的 group→episode，沿用既有确认失效与结构事务要求。本次不增加表或列，详见[录入交互规则](../ingest-interaction-v07.md)。
