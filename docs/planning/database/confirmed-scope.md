# 已确认范围与旧数据来源 · 2026-11-16

本次确认已同步到 v0.4 候选结构、逐字段依据、字段字典和旧字段去向。首版仍面向个人自用、Web + Android、当前 Mac 部署；候选 SQL 不是已经接入应用的 migration。用户随后确认旧观看进度也不迁移，完整新规则见[观看进度与继续播放](../playback.md)。

## 1 账号与个人资料：通用单账号

保留账号、默认个人资料、设备标识、登录会话的通用职责。首版初始化一个账号和一个默认 profile，两个客户端共享同一套个人状态；设备只用于识别播放来源和管理登录会话。

不实现注册、邀请、账号切换、多 profile 切换、角色权限或公网账号管理。表结构允许日后扩展，不需要现在把多账号流程做出来。外网出站抓取仍按来源配置处理。

## 2 上下部 / Part1、Part2：有序分集

用户已确认现有 14 组父子资料都按集理解，首版使用：

```text
作品组 group
  第 1 集 episode → 默认播放版本 edition → 文件
  第 2 集 episode → 默认播放版本 edition → 文件
  第 3 集 episode → 默认播放版本 edition → 文件
```

- 旧父记录进入 group，原封面、标题、分类、演职员、系列、喜欢和评分等信息保留在相应主体。
- 旧子记录进入 episode；parent_movie_code 转 parent_id，episode_order 转 episode_number。字幕、文件和精确断点属于实际可播放的集及其版本。
- 不为这些作品生成“第一季”。未来真实电视剧可以直接 show→episode，也可以按真实资料使用 show→season→episode；季是可选组织层。
- “分集”和“同一集的多个物理文件段”分开：Part1/Part2 已明确是集时，各自建立版本；每个单文件版本只有 part_no=1。只有同一集确实被切成多个文件时才使用多条 edition_parts。
- 组、剧、季是组织容器，不直接建立播放版本。组页的继续观看从子集新系统中的有效未完成断点定位，不把某集断点复制成组的虚假播放版本，也不以旧 last_played_at 生成续播。
- 父项和子集的既有喜欢、评分分别保留，不把父项的个人状态复制到所有子集，也不重复累计父项汇总与子集播放次数。

数据盘点仍需注意：历史备份中 12 个父项另有非空 file_path，文本值与各自子项路径不相同；这不能仅凭路径证明存在额外一集。旧查询在存在子项时只返回子项为 episodes。迁移时保留这些原始路径并登记文件盘点，不自动新增“第 0 集”，也不删除任何原文件。内容的分集语义已经确认，文件绑定需单独核对。

## 3 人物扩展：后置

首版使用 full_name、detailed_name、头像、已存在的性别与分类等信息。生日、人物简介、角色名等无现有数据的内容后置；无需为了空字段添加表单、抓取能力或页面占位。

候选定义可保留可空列以说明扩展方向，首版接口不开放其编辑，正式 migration 按实现范围裁剪。未来需要时增加可空字段或专用关系，不影响已确定的两个名称及作品关联。独立 genre、网站评分、NFO 和外挂字幕绑定等也继续后置，不要求迁入不存在的数据。

## 4 旧任务：全部不迁移

明确排除：task、actor_profile_task 的全部行，以及两个表的 result_url 指向的 JSON 结果文件。状态、百分比、错误、开始/结束记录和旧任务 ID 均不进入新系统，也不恢复旧的进行中任务。

新系统仍需要任务中心和持久检查点，从切换后的真实新任务开始记录。旧任务的功能职责可以作为新设计依据，但不是把旧任务数据搬过去。已发布到 movie、actor、series、tag 等正式资料中的内容继续按正式资料迁移，不因旧任务排除而一起丢弃。

## 5 三项旧数据问题从哪里来

### 观看进度百分比

来源：`movie.watch_progress`。旧实体定义为 0～100；[播放行为服务](../../../../home-media/apps/backend/src/service/movie/movie-engagement.service.ts)会对上报 progress 取整并限定范围，完播时写 100。旧实体另有 `last_play_position_ms` 保存毫秒位置。

仓库文件名日期为 2026-09-29 的 SQL 备份只有百分比字段，没有后来新增的毫秒位置列。备份中 3 条记录分别为 33、49、6，其余为 0。这是历史快照，不能用来断言当前运行库缺少精确断点。

因此此前“旧百分比断点”的说法应读作“旧观看进度，可能不足以恢复精确位置”。用户进一步确认旧客户端继续播放有缺陷，新系统不迁入 watch_progress 或 last_play_position_ms，也不换算或生成迁移专用会话。旧库备份保留原值；新系统从真实播放重新建立进度，初始续播入口为空。

### 格式化文件大小

来源：`movie.file_size` 是 varchar。旧[本地解析服务](../../../../home-media/apps/backend/src/service/task/local.service.ts)先 `fs.stat(filePath)` 取得 stat.size，再调用 `formatFileSize`；该函数按 1024 换算并默认保留两位小数，最后返回带 GB/MB 单位的字符串。

例如 `2.34 GB` 是格式示例，不是引用某条影片数据。它适合显示，不能反推原始精确字节数。新 media_files.size_bytes 从实际文件重新 stat 获取，页面显示时再格式化；文件离线进入待核验，不伪造精确大小。原字符串在迁移导出中保留。

### 喜欢时间未知

来源不是一个旧“未知时间”字段，而是缺少对应记录。旧影片只有 `movie.is_favorite`，人物只有 `actor.is_collected`；[影片实体](../../../../home-media/packages/entities/src/movie.entity.ts)和[演员实体](../../../../home-media/packages/entities/src/actor.entity.ts)均没有 favorited_at。它们的 created_at/updated_at 还可能因其他资料修改变化，不能当作喜欢发生时间；收藏夹关系创建时间也不等于影片喜欢时间。

新 `favorited_at` 是为“按最近喜欢排序”增加的可空时间。旧 is_favorite=true 可以配 favorited_at=NULL，仍然是喜欢，只是日期未知；新喜欢动作写真实服务端时间，取消时清空。不要求补录历史日期，也不以时间为空取消喜欢状态。

## 7 分类、人工发布与播放范围 · 2026-11-17

- 用户确认作品、演员各属一个分类，用 primary_category_id 表达；未指定时使用系统“未分类”。观看端提供“全部、喜剧片、动作片……”单选分类筛选；这些名称可直接使用 categories，无需首版启用独立 genres。演员自身分类与其作品分类分别筛选，不互相复制归属。
- 所有入库均须人工确认、手动发布。扫描/探测/抓取可后台执行，只产生候选和草稿；ready 仍等待发布动作。可核对后主动批量发布，草稿/候选变化需重新复核；重启和重试只恢复同一次已授权发布，不新建自动发布决定。
- 已入库资料刷新沿用人工接受差异与字段锁定规则，抓取完成不自动改正式资料。
- 用户确认首版面向 MP4、MKV 等常见文件、依靠原生播放。实现范围收敛为识别入库和 direct/unsupported；转码与服务端 remux 后置。容器、编码和客户端能力共同决定能否播放，不能保证所有 MKV 在所有浏览器可播。详见[播放兼容与验收基线](../playback.md)。
- 分类隐藏已进一步明确：用于收起暂时没有影片的入口，保留手动配置；有影片时提示后允许继续隐藏，具体规则见下节。系列沿用单主分类方案。

这次确认不改变候选表数、字段数或外键，尚未新增数据库或播放器实测。后续工作集中在首版技术裁剪和实际样例验证。

## 8 分类隐藏提示 · 2026-11-17

用户确认保留分类显示/隐藏开关。空分类可直接隐藏；从显示改为隐藏时，如果该分类或子分类下有影片，提示总数与本级/子分类数量，可取消或继续隐藏。隐藏只收起导航入口，全部片库、搜索和演员页仍可找到作品，管理端可随时重新显示。

计数与观看列表一致：已发布、未归档，按作品去重，离线作品及已隐藏子分类仍计入；草稿不计，不按版本或文件重复计算。保存时重新核对预览，变化则更新提示。开关由人工维护，不根据空/非空自动切换。

现有 categories.is_visible 已能承接，无需增加字段。HTML 原型已补齐列表快捷开关和编辑表单两条路径；本地交互测试覆盖空分类、有影片含后代、取消、确认、编辑输入保留、提示期间资料变化以及重新显示。正式 API/数据库事务校验尚待实现。
